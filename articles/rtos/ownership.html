La propriété, les tâches et les objets de synchronisation

Lors de la création d'une tâche ou d'un objet de synchronisation, le noyau Mk a la possibilité de définir un propriétaire.

Ce propriétaire est stocké dans le champ owner des tâches et dans le champ createByAddr des objets de synchronisation. Son but est de référencer l'ensemble des tâches et l'ensemble des objets qui appartiennent à une même application.

Le tableau ci-dessous décrit quel attribut est utilisé pour stocker le propriétaire d'une tâche ou d'un objet :

Objet Structure Attribut
Tâche T_mkTask owner
Mutex T_mkMutex createByAddr
Sémaphore T_mkSemaphore createByAddr
Champ d'événements T_mkEvent createByAddr
Boîte de messages T_mkMail createByAddr
Pool T_mkPool createByAddr
Gestionnaire de rappel T_mkCallbackHandler createByAddr
Fonction de rappel T_mkCallback createByAddr

1. Le propriétaire d'une tâche

Le propriétaire d'une tâche est défini lors de sa création en utilisant le paramètre p_mkOwner de la fonction mk_task_setTaskCtrlBlock : 


T_mkCode mk_task_setTaskCtrlBlock ( T_mkTaskCtrlBlock* p_mkAttribute, 
   uint32_t p_mkType, uint32_t p_mkIdentifier, uint32_t p_mkPriority, 
   T_mkAddr p_mkOwner );

Ce paramètre est enregistré dans l'attribut owner de la tâche. Il est optionnel et peut prendre la valeur K_MK_NULL si la tâche ne nécessite pas de propriétaire.


Les propriétaires sont hérités. Lorsqu'une tâche qui possède un propriétaire en crée une autre, le paramètre p_mkOwner est ignoré et la nouvelle tâche hérite du propriétaire de la tâche créatrice. Le paramètre n'est donc pris en compte que lorsque la tâche créatrice n'en possède pas déjà un.


⚠️

Cette règle n'est pas applicable aux vecteurs d'interruption. Une tâche créée depuis une interruption reçoit toujours le propriétaire passé en paramètre.


Le noyau n'interprète pas la valeur du propriétaire. Il s'agit d'une adresse quelconque, à la disposition de l'utilisateur. Dans le cas d'une application, le propriétaire peut par exemple être l'adresse d'une structure applicative.


L'héritage garantit qu'une tâche ne peut pas échapper à son application étant donné que toutes les tâches créées directement ou indirectement par la tâche principale de l'application partagent le même propriétaire.

2. Le propriétaire d'un objet de synchronisation

Lors de la création d'un objet, le noyau copie la valeur de l'attribut owner de la tâche qui a exécuté l'appel système dans l'attribut createByAddr.

L'objet hérite donc du propriétaire de la tâche appelante et non de l'adresse de la tâche créatrice. Deux conséquences en découlent :

  • ✔Tous les objets créés par les tâches d'une même application partagent la même valeur de createByAddr.
  • ✔Si la tâche appelante n'a pas de propriétaire, l'attribut createByAddr de l'objet est nul.

3. L'arbre de création

La propriété est transmise par héritage. L'application attribue d'abord un propriétaire à sa tâche principale qui le transmet aux tâches qu'elle crée et aux objets qu'elle alloue. On obtient ainsi un arbre dont la racine est l'application : 


Application (T_mkApplication)
 ├─ Tâche principale                  owner = Application
 │   ├─ Mutex                         createByAddr = Application
 │   ├─ Boîte de messages             createByAddr = Application
 │   ├─ Tâche secondaire              owner = Application (hérité)
 │   │   └─ Sémaphore                 createByAddr = Application
 │   └─ Gestionnaire de rappel        createByAddr = Application
 │       ├─ Champ d'événements        createByAddr = Application
 │       └─ Fonction de rappel        createByAddr = Application
 └─ ...

Il suffit alors de comparer le propriétaire d'une tâche ou d'un objet avec l'adresse de l'application pour déterminer son origine. Il devient alors possible d'identifier les tâches et les objets de synchronisation qui ont été créés et qui doivent être supprimés suite à la fermeture d'une application.

4. Limitations

Le mécanisme de propriétaire connaît les limitations suivantes :

  • ✔Lors de la création d'un gestionnaire d'allocation mémoire ou d'une boîte de messages, la zone mémoire fournie par l'utilisateur ne se voit pas attribuer de propriétaire (T_mkPoolArea).
  • ✔Étant donné que les fonctions de rappel sont créées séparément des gestionnaires de rappel, leur propriétaire peut être différent de celui du gestionnaire auquel elles sont rattachées.
  • ✔La propriété et la protection sont deux notions distinctes. Un objet non protégé peut être manipulé par toutes les tâches, quel que soit son propriétaire.

5. Utilisation

L'exemple ci-dessous montre comment attribuer un propriétaire à la tâche principale d'une application : 


/* On définit le type T_mkApplication pour l'exemple */
/* Celui-ci possède les attributs de la tâche principale et d'autres */
/* si nécessaire */
typedef struct T_mkApplication T_mkApplication;
struct T_mkApplication
{
   T_mkTask*   task;          /*!< Adresse de la tâche principale. */
   T_mkStack   stack;         /*!< Caractéristiques de la pile. */
   uint32_t    identifier;    /*!< Identifiant de la tâche principale. */
   uint32_t    type;          /*!< Type de la tâche principale. */
   uint32_t    priority;      /*!< Priorité de la tâche principale. */
   T_mkAddress entryAddr;     /*!< Point d'entrée de la tâche principale. */
   T_mkAddr    arg;           /*!< Argument de la tâche principale. */
};

/* Déclaration et initialisation de l'application */
T_mkApplication g_application;

/* ... */

/* Configuration du TCB de la tâche principale de l'application */
/* On écrit l'adresse de g_application dans le propriétaire */
T_mkCode l_result;
T_mkTaskCtrlBlock l_taskCtrlBlock;
l_result = mk_task_setTaskCtrlBlock ( &l_taskCtrlBlock, 
   g_application.type, g_application.identifier, g_application.priority, 
   &g_application );

/* ... */

/* Création de la tâche ... */
l_result |= mk_task_create ( &g_application.task, &g_application.stack, 
   K_MK_NULL, &l_taskCtrlBlock, g_application.entryAddr, 
   g_application.arg );

Suite à sa création, la tâche principale possède g_application comme propriétaire. Celui-ci se propagera donc à tous ses enfants : 


/* Point d'entrée de l'application (tâche principale, owner = application) */
void application_main ( T_mkAddr p_param )
{
   /* Déclaration des variables de travail */
   T_mkCode l_result;
   T_mkTaskCtrlBlock l_taskCtrlBlock;

   /* Création d'un mutex (createByAddr = &g_application) */
   l_result = mk_mutex_create ( &g_mutex, K_MK_AREA_UNPROTECTED );

   /* Configuration d'une tâche secondaire. Le propriétaire passé en  */
   /* paramètre est ignoré car la tâche courante possède déjà */
   /* un propriétaire */
   l_result = mk_task_setTaskCtrlBlock ( &l_taskCtrlBlock, 
      K_MK_TYPE_DEFAULT, 10, 2, K_MK_NULL );

   /* ... */

   /* Création de la tâche secondaire (owner = &g_application) */
   l_result = mk_task_create ( &g_task, &g_stack, K_MK_NULL, 
      &l_taskCtrlBlock, application_worker, K_MK_NULL );

   /* ... */
   for ( ;; ) ;
}

6. Le stockage des tâches et des objets

Les tâches et les objets de synchronisation sont déclarés statiquement à la compilation dans des gestionnaires d'allocation de taille fixe. Leur nombre est donc fini et une application peut parcourir chaque objet afin d'évaluer les liens de propriété. Le tableau ci-dessous contient la désignation de l'ensemble des gestionnaires d'allocation :

Objet Gestionnaire Tableau Nombre de blocs
Tâche g_mkTaskPool task K_MK_SCHEDULER_MAX_NUMBER_OF_TASKS
Mutex g_mkMutexPool mutex K_MK_SCHEDULER_MAX_NUMBER_OF_MUTEX
Sémaphore g_mkSemaphorePool semaphore K_MK_SCHEDULER_MAX_NUMBER_OF_SEMAPHORES
Champ d'événements g_mkEventPool event K_MK_SCHEDULER_MAX_NUMBER_OF_EVENTS
Boîte de messages g_mkMailPool mail K_MK_SCHEDULER_MAX_NUMBER_OF_MAILS
Item de boîte de messages g_mkMailItemPool item K_MK_SCHEDULER_MAX_NUMBER_OF_ITEMS
Pool g_mkAreaPool poolArea K_MK_SCHEDULER_MAX_NUMBER_OF_POOLS
Gestionnaire de rappel g_mkCallbackHandlerPool handler K_MK_SCHEDULER_MAX_NUMBER_OF_CALLBACK_HANDLERS
Fonction de rappel g_mkCallbackFunctionPool callback K_MK_SCHEDULER_MAX_NUMBER_OF_CALLBACK_FUNCTIONS

Chaque gestionnaire est composé d'une structure T_mkPoolArea qui décrit la zone mémoire, d'une structure T_mkPool qui gère l'allocation et d'un tableau qui contient les objets. Ces derniers peuvent être parcourus pour relier une application et les objets créés par celle-ci.


L'exemple ci-dessous recherche l'ensemble des tâches créées par une application. La fonction parcourt le tableau des tâches puis compare l'attribut owner de chacune avec l'adresse de l'application. Elle enregistre ensuite les tâches trouvées dans un tableau fourni par l'appelant : 


/* Fonction recherchant les tâches créées par une application */
uint32_t mk_application_findTasks ( T_mkApplication* p_application, 
   T_mkTask** p_tasks, uint32_t p_size )
{
   /* Déclaration des variables de travail */
   uint32_t l_counter;
   uint32_t l_number = 0;

   /* Déclaration d'un pointeur de tâche */
   T_mkTask* l_task;

   /* Entrée en section critique - masque des interruptions */
   /* Cette fonction est sans effet en mode non privilégié */
   ( void ) _mk_scheduler_mask ( K_MK_SCHEDULER_MASK_PRIORITY );

   /* Pour toutes les tâches du gestionnaire d'allocation */
   for ( l_counter = 0 ; 
      l_counter < K_MK_SCHEDULER_MAX_NUMBER_OF_TASKS ; l_counter++ )
   {
      /* Récupération de l'adresse de la tâche */
      l_task = &g_mkTaskPool.task [ l_counter ];

      /* Si la tâche est allouée et si elle appartient à l'application */
      if ( ( l_task->owner == ( T_mkAddr ) p_application ) &&
            ( l_task->attribute.state != K_MK_STATE_DELETED ) )
      {
         /* Si le tableau de sortie peut recevoir la tâche */
         if ( l_number < p_size )
         {
            /* Enregistrement de l'adresse de la tâche */
            p_tasks [ l_number ] = l_task;
         }

         /* Actualisation du nombre de tâches trouvées */
         l_number++;
      }
   }

   /* Sortie de la section critique - démasquage des interruptions */
   /* Cette fonction est sans effet en mode non privilégié */
   ( void ) _mk_scheduler_unmask ( K_MK_SCHEDULER_IDLE_PRIORITY );

   /* Retour */
   return ( l_number );
}

L'exemple ci-dessous applique le même principe aux sémaphores. Lors de sa suppression, un sémaphore est rempli avec la valeur K_MK_INVALID_HANDLE (à l'exception du premier mot, utilisé par la pool). Son attribut createByAddr ne peut donc pas correspondre à l'adresse d'une application : 


/* Fonction recherchant les sémaphores créés par une application */
/* Elle retourne le nombre de sémaphores appartenant à l'application */
uint32_t mk_application_findSemaphores ( T_mkApplication* p_application, 
   T_mkSemaphore** p_semaphores, uint32_t p_size )
{
   /* Déclaration des variables de travail */
   uint32_t l_counter;
   uint32_t l_number = 0;

   /* Déclaration d'un pointeur de sémaphore */
   T_mkSemaphore* l_semaphore;

   /* Entrée en section critique - masque des interruptions */
   /* Cette fonction est sans effet en mode non privilégié */
   ( void ) _mk_scheduler_mask ( K_MK_SCHEDULER_MASK_PRIORITY );

   /* Pour tous les sémaphores du gestionnaire d'allocation */
   for ( l_counter = 0 ; 
      l_counter < K_MK_SCHEDULER_MAX_NUMBER_OF_SEMAPHORES ; l_counter++ )
   {
      /* Récupération de l'adresse du sémaphore */
      l_semaphore = &g_mkSemaphorePool.semaphore [ l_counter ];

      /* Si le sémaphore appartient à l'application */
      if ( l_semaphore->createByAddr == ( T_mkAddr ) p_application )
      {
         /* Si le tableau de sortie peut recevoir le sémaphore */
         if ( l_number < p_size )
         {
            /* Enregistrement de l'adresse du sémaphore */
            p_semaphores [ l_number ] = l_semaphore;
         }

         /* Actualisation du nombre de sémaphores trouvés */
         l_number++;
      }
   }

   /* Sortie de la section critique - démasquage des interruptions */
   /* Cette fonction est sans effet en mode non privilégié */
   ( void ) _mk_scheduler_unmask ( K_MK_SCHEDULER_IDLE_PRIORITY );

   /* Retour */
   return ( l_number );
}

Les deux fonctions masquent les interruptions pendant le parcours des gestionnaires afin d'empêcher le déclenchement d'un appel système par une tâche concurrente qui pourrait venir modifier ces structures. La section critique doit rester la plus courte possible. Du fait des caractéristiques des fonctions _mk_scheduler_mask et _mk_scheduler_unmask, la recherche ne peut être faite que par une tâche privilégiée.
