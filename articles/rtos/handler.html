Traiter les erreurs avec les gestionnaires

Le module handler regroupe les gestionnaires d'erreurs du noyau. Il permet à l'application d'être prévenue lorsqu'une erreur interne, une exception matérielle ou une violation de permissions se produit.

1. Synthèse des fonctions

Ce module est constitué d'un ensemble de fonctions de rappel qui peuvent être surchargées par l'application. Ces fonctions sont déclarées dans les fichiers mk_handler_private.h et mk_handler.h :

Fonction Description
mk_handler_nmiFault Gestionnaire d'erreur de l'exception NMI.
mk_handler_hardFault Gestionnaire d'erreur de l'exception HardFault.
mk_handler_busFault Gestionnaire d'erreur de l'exception BusFault.
mk_handler_memFault Gestionnaire d'erreur de l'exception MemManageFault.
mk_handler_usageFault Gestionnaire d'erreur de l'exception UsageFault.
mk_handler_fpuFault Gestionnaire d'erreur de l'exception FPU.
mk_handler_stackFault Gestionnaire d'erreur de dépassement de pile.
mk_handler_rightFault Gestionnaire d'erreur pour des droits insuffisants.
mk_handler_handleFault Gestionnaire d'erreur pour une instance invalide.
mk_handler_kernelFault Gestionnaire d'erreur interne du noyau.
mk_handler_callbackFault Gestionnaire d'erreur pour les managers de rappel.
mk_handler_set Référence les fonctions de rappel de l'application dans le noyau.

2. Fonctionnement

Lorsqu'une erreur grave est détectée, le noyau exécute le gestionnaire mk_handler_xxxFault correspondant à l'erreur. La donnée g_mkKernelCallback est alors analysée pour déterminer si une fonction de rappel a été personnalisée par l'application.

Si une fonction a été personnalisée, le noyau l'exécute. Dans le cas contraire et en fonction de la criticité de l'erreur, le noyau se bloque ou ne réalise aucune action.


💬

Les gestionnaires du noyau ne sont pas modifiables. Pour personnaliser le traitement d'une erreur, l'application doit référencer ses propres routines en utilisant la fonction mk_handler_set.


Le tableau ci-dessous liste l'ensemble des gestionnaires d'erreurs du noyau, leur comportement par défaut et les actions recommandées pour les traiter :

Fonction de rappel Origine de l'erreur Comportement
par défaut		 Comportement
recommandé
nmiFault Exception matérielle NMI. Blocage. Reset.
hardFault Exception matérielle HardFault. Blocage. Suspension de la tâche fautive ou reset.
busFault Exception matérielle BusFault. Blocage. Suspension de la tâche fautive ou reset.
memFault* Exception matérielle MemManageFault. Blocage. Suspension de la tâche fautive ou reset.
usageFault Exception matérielle UsageFault. Blocage. Suspension de la tâche fautive ou reset.
fpuFault Exception matérielle de l'unité de calcul flottant. Blocage. Suspension de la tâche fautive ou reset.
kernelFault Erreur interne du noyau. Blocage. Reset.
stackFault Dépassement de pile. Blocage. Suspension de la tâche fautive ou reset.
rightFault Appel système réalisé avec un niveau de droits insuffisant. Aucune action. Déclenchement de l'exception MemManageFault.
handleFault Appel système réalisé avec une instance invalide. Aucune action. Déclenchement de l'exception MemManageFault.
callbackFault Erreur interne du module de fonctions de rappel. Aucune action. Suspension de la tâche fautive ou reset.

* Cette exception peut être déclenchée suite à une violation d'accès détectée par la MPU ou explicitement par un autre gestionnaire.


Les exceptions matérielles nmiFault, hardFault, busFault, memFault, usageFault et fpuFault sont directement déclenchées par le processeur. Leur adresse doit être référencée dans la table des vecteurs d'interruption.


Pour la majorité des erreurs, le comportement recommandé consiste à suspendre la tâche fautive si celle-ci est non privilégiée ou effectuer un reset si l'erreur s'est produite dans une tâche privilégiée ou dans un vecteur d'interruption.


Pour les erreurs nmiFault et kernelFault, un reset est recommandé car ces erreurs sont suffisamment graves pour ne pas pouvoir être récupérées, l'erreur NMI signifiant l'échec d'une des exceptions logicielles et une kernelFault une corruption critique du noyau.


L'erreur stackFault peut provoquer une corruption des données et déclencher des dysfonctionnements à la chaîne. Un reset doit donc être réalisé lorsqu'un dépassement se produit sur une pile privilégiée. Pour les tâches non privilégiées, une suspension est tolérée car les données privilégiées sont protégées en continu par la MPU d'une corruption non privilégiée.


L'erreur callbackFault se déclenche lorsque les gestionnaires ou les fonctions de rappel n'ont pas été correctement supprimés par l'application ou lorsque les données des managers ont été corrompues par un dépassement de pile. Cette erreur peut être gérée par reset ou par suspension du manager fautif.


Enfin, les erreurs rightFault et handleFault sont déclenchées directement par le noyau pendant les appels système. L'application ne peut donc pas gérer l'erreur en réalisant un autre appel système.


⚠️

L'exécution d'appels système est interdite dans les fonctions de rappel rightFault et handleFault. La suspension de la tâche fautive doit être déléguée au vecteur d'interruption MemManageFault. Cette méthode est détaillée dans l'article Protéger son programme avec Mk.


⚠️

Une exception matérielle qui n'est pas traitée se déclenche de nouveau dès la fin de son vecteur d'interruption. Le blocage permet de stopper cette répétition intempestive.


💬

Les fonctions de rappel sont exécutées en mode privilégié. Elles doivent donc être courtes et ne jamais se bloquer.


3. Utilisation

Les fonctions de rappel peuvent être référencées avec la fonction mk_handler_set. Cette fonction copie une structure T_mkKernelCallback dans la donnée du noyau g_mkKernelCallback. L'exemple ci-dessous montre comment l'utiliser : 



T_mkCode mk_fault_initHandlers ( void )
{
   T_mkCode l_result;
   /* Initialisation de la structure */
   /* La valeur K_MK_NULL permet de conserver le comportement par défaut */
   /* du noyau (boucle infinie ou aucune action)  */
   T_mkKernelCallback l_kernelCallbackHandler = { K_MK_NULL };
   l_kernelCallbackHandler.busFault = mk_busFault;
   l_kernelCallbackHandler.callbackFault = mk_callbackFault;
   l_kernelCallbackHandler.fpuFault = mk_fpuFault;
   l_kernelCallbackHandler.handleFault = mk_handleFault;
   l_kernelCallbackHandler.hardFault = mk_hardFault;
   l_kernelCallbackHandler.kernelFault = mk_kernelFault;
   l_kernelCallbackHandler.memFault = mk_memFault;
   l_kernelCallbackHandler.nmiFault = mk_nmiFault;
   l_kernelCallbackHandler.rightFault = mk_rightFault;
   l_kernelCallbackHandler.stackFault = mk_stackFault;
   l_kernelCallbackHandler.usageFault = mk_usageFault;

   /* Référencement des gestionnaires d'erreur du noyau */
   l_result = mk_handler_set ( &l_kernelCallbackHandler );
   return ( l_result );
}

⚠️

La fonction mk_handler_set ne déclenche pas d'appel système. Elle doit être exécutée depuis une tâche privilégiée ou depuis le programme principal. Une tâche non privilégiée qui l'exécute provoque une violation d'accès mémoire.


Les fonctions de rappel sont exécutées en mode privilégié. Elles doivent s'exécuter le plus rapidement possible. Le code ci-dessous présente une implémentation de tous ces gestionnaires : 


void mk_handleDefaultFault ( void )
{
   /* Si la tâche courante est une tâche non privilégiée */
   if ( ( g_mkScheduler.statusRegister.isr == 0 ) && 
      ( g_mkScheduler.currentTask != K_MK_NULL ) &&
      ( ( g_mkScheduler.currentTask->attribute.type & K_MK_TYPE_PRIVILEGED )
      == K_MK_TYPE_DEFAULT ) )
   {
      /* On suspend la tâche qui a provoqué l'erreur */
      ( void ) mk_task_suspend ( g_mkScheduler.currentTask );
   }

   /* Sinon */
   else
   {
      /* On reset le programme */
      cortex_resetSystem ( );
   }
}

void mk_busFault ( void )
{
   /* Exécution du gestionnaire d'erreur */
   mk_handleDefaultFault ( );
}

void mk_memFault ( void )
{
   /* Exécution du gestionnaire d'erreur */
   mk_handleDefaultFault ( );
}

void mk_fpuFault ( void )
{
   /* Exécution du gestionnaire d'erreur */
   mk_handleDefaultFault ( );
}

void mk_usageFault ( void )
{
   /* Exécution du gestionnaire d'erreur */
   mk_handleDefaultFault ( );
}

void mk_hardFault ( void )
{
   /* Exécution du gestionnaire d'erreur */
   mk_handleDefaultFault ( );
}

void mk_nmiFault ( void )
{
   /* On reset le programme */
   cortex_resetSystem ( );
}

void mk_stackFault ( void )
{
   /* Exécution du gestionnaire d'erreur */
   mk_handleDefaultFault ( );
}

void mk_callbackFault ( T_mkCode p_mkResult )
{
   /* Le paramètre p_mkResult contient la valeur du code de retour */
   /* ayant déclenché l'erreur. */

   /* Exécution du gestionnaire d'erreur */
   mk_handleDefaultFault ( );
}

void mk_handleFault ( T_mkAddr p_mkHandle )
{
   /* Le paramètre p_mkHandle contient l'adresse de l'instance */
   /* ayant déclenché l'erreur. */
   
   /* L'interruption matérielle MemManageFault sera déclenchée */
   /* après la fin du changement de contexte */
   nvic_setPendingException ( K_NVIC_PENDING_MEMFAULT );
}

void mk_rightFault ( void )
{
   /* L'interruption matérielle MemManageFault sera déclenchée */
   /* après la fin du changement de contexte */
   nvic_setPendingException ( K_NVIC_PENDING_MEMFAULT );
}

void mk_kernelFault ( 
   T_mkKernelError p_mkCode, T_mkSVCObject* p_mkObject, uint32_t p_mkStatus )
{
   /* Les 3 paramètres permettent de déboguer l'erreur rencontrée */
   /* - p_mkCode contient le type de l'erreur  */
   /* - p_mkObject contient l'adresse de l'objet SVC manipulé. */
   /* - p_mkStatus indique l'origine de l'appel système (vecteur */
   /*   d'interruption ou tâche). */
   
   /* On reset le programme */
   cortex_resetSystem ( );
}

Les fonctions de rappel handleFault et callbackFault reçoivent chacune un paramètre. Celui-ci contient l'adresse de l'instance invalide pour la première et la valeur du code de retour pour la seconde fonction.


La fonction de rappel kernelFault possède trois paramètres. Le premier contient le code de l'erreur (T_mkKernelError), le deuxième l'adresse de l'objet SVC décrivant l'appel système en cours (T_mkSVCObject) et le troisième paramètre indique si l'appel système a été réalisé dans un vecteur d'interruption ou non.


⚠️

Une erreur kernelFault signale un état incohérent des structures internes du noyau. Après l'exécution de la fonction de rappel, il est fortement conseillé de redémarrer le processeur.


💬

Pour les exceptions matérielles, aucune information n'est transmise à la fonction de rappel. C'est à l'application de lire les registres du processeur (par exemple CFSR ou MMFAR) pour déterminer la source de l'erreur.


4. API

4.1. La fonction mk_handler_set()

Cette fonction référence les fonctions de rappel de l'application dans le noyau. Elle copie la structure T_mkKernelCallback fournie par l'application dans la structure g_mkKernelCallback.


Prototype :


T_mkCode mk_handler_set ( T_mkKernelCallback* p_kernelCallback );

Paramètres :

  • p_kernelCallback [in]

    Adresse d'une structure de type T_mkKernelCallback.

Retour :

  • K_MK_OK : les fonctions de rappel de l'application ont été référencées.
  • K_MK_ERROR_PARAM : les fonctions de rappel de l'application n'ont pas été référencées car le paramètre est invalide.

Note :

  • Cette fonction doit être exécutée par une tâche privilégiée.
  • Cette fonction copie l'intégralité de la structure. Les fonctions de rappel référencées lors d'un appel précédent sont donc écrasées.
