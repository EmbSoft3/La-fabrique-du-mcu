Différer l'exécution des fonctions avec les Callbacks

Le module callback permet de différer l'exécution d'une ou plusieurs fonctions dans une tâche dédiée du noyau et d'attendre la fin de leur exécution. Cette page détaille le fonctionnement et l'utilisation des fonctions de ce module.

1. Synthèse des fonctions

Les fonctions de ce module sont déclarées dans le fichier mk_callback.h :

Fonction Description
mk_callback_createManagers Crée les deux managers de rappel.
mk_callback_createHandler Crée un gestionnaire de rappel.
mk_callback_create Crée une fonction de rappel.
mk_callback_trig Déclenche l'exécution d'une fonction de rappel.
mk_callback_wait Attend l'exécution d'une ou plusieurs fonctions de rappel.
mk_callback_delete Supprime une fonction de rappel.
mk_callback_deleteHandler Supprime un gestionnaire de rappel.

2. Fonctionnement

Une fonction de rappel (callback) est une fonction dont l'exécution est différée. C'est-à-dire que la tâche qui la déclenche n'attend pas qu'elle se termine. Elle est exécutée en parallèle de celle-ci dans un autre contexte du noyau. Lorsque son travail est terminé, la tâche émettrice peut décider d'attendre la fin de l'exécution de cette fonction.


Le module callback repose sur deux types d'objets alloués par le noyau dans l'espace privilégié :

  • ✔Le gestionnaire de rappel qui regroupe un ensemble de fonctions de rappel. Il est associé à un champ d'événements de type MULTI qui permet d'attendre la fin de l'exécution de chaque fonction.
  • ✔La fonction de rappel qui référence l'adresse de la fonction et le gestionnaire auquel elle appartient et qui possède un identifiant unique au sein de son gestionnaire.

Les managers de rappel

L'exécution des fonctions de rappel est confiée à deux managers créés à l'initialisation du noyau avec la fonction mk_callback_createManagers. Un manager est constitué d'une tâche, de sa pile et d'une boîte de messages. Les caractéristiques des deux managers sont les suivantes :

Manager Tâche Boîte de messages Exécute les
fonctions de rappel
g_mkPrivilegedCallbackManager Privilégiée Protégée En mode privilégié
g_mkUnPrivilegedCallbackManager Non privilégiée Non protégée En mode non privilégié

Par défaut, les deux tâches possèdent la même priorité et une pile de 4 Ko. Leur type (flottant ou non flottant) est choisi à l'initialisation du noyau. Une fonction de rappel utilisant la FPU impose donc d'initialiser les managers en mode flottant.


💬

Le nombre de gestionnaires et de fonctions de rappel pouvant être alloués par le noyau est limité. Ils sont définis à la compilation par la constante K_MK_SCHEDULER_MAX_NUMBER_OF_CALLBACK_HANDLERS et la constante K_MK_SCHEDULER_MAX_NUMBER_OF_CALLBACK_FUNCTIONS.

Attribution d'un manager

Le manager qui exécutera les fonctions d'un gestionnaire de rappel est choisi lors de la création de celui-ci et ne peut plus être modifié par la suite :

  • ✔Un gestionnaire protégé créé par une tâche privilégiée est rattaché au manager privilégié. Ses fonctions seront exécutées en mode privilégié.
  • ✔Dans tous les autres cas, le gestionnaire est rattaché au manager non privilégié. Ses fonctions sont exécutées en mode non privilégié et les restrictions de la MPU s'appliquent.

Plusieurs gestionnaires peuvent être rattachés au même manager. Ils partagent alors sa boîte de messages et sa tâche.

Le mécanisme de rappel

Lorsque l'exécution d'une fonction de rappel est demandée (mk_callback_trig), un message est posté dans la boîte de messages du manager référencé dans le gestionnaire. Ce message contient l'adresse de la fonction de rappel et la valeur des paramètres à lui transmettre.

Suite à la réception du message, le manager exécute la fonction demandée puis positionne l'identifiant de la fonction de rappel dans le champ d'événements du gestionnaire. Les tâches bloquées par la fonction mk_callback_wait sont alors réveillées.


💬

Une fonction de rappel peut être exécutée avant même que la tâche n'ait appelé la fonction mk_callback_wait. Comme pour tous les champs d'événements, l'identifiant reste positionné jusqu'à ce qu'il soit consommé par un wait ou remis à zéro explicitement.


💬

Chaque boîte de messages d'un manager peut contenir un nombre limité de messages. Lorsque la boîte est pleine, le déclenchement d'une nouvelle fonction de rappel est temporisé jusqu'à ce qu'un emplacement se libère.


⚠️

Les fonctions de rappel d'un même manager sont exécutées séquentiellement dans la même tâche (algorithme FIFO). Une fonction de rappel doit donc être courte et ne jamais se bloquer indéfiniment. Elle doit aussi être compatible avec la taille de la pile de son manager.


⚠️

En cas d'erreur grave dans un manager (échec de la lecture d'un message ou du positionnement de l'événement), le noyau exécute la routine mk_handler_callbackFault.


Les fonctions de rappel possèdent toutes le même prototype. Celui-ci est constitué de six paramètres pouvant être implémentés ou non par l'application : 


void callback ( T_mkAddr p_param1, T_mkAddr p_param2, T_mkAddr p_param3,
   T_mkAddr p_param4, T_mkAddr p_param5, T_mkAddr p_param6 );

💬

Pour transmettre un volume important de données, il est préférable de passer l'adresse d'un bloc mémoire dans un des paramètres.

3. Avantages et inconvénients

Les fonctions de rappel possèdent les avantages suivants :

  • ✔Elles permettent de déporter un traitement dans le contexte d'une tâche plutôt que de l'exécuter dans le contexte de celui qui le déclenche.
  • ✔Elles permettent d'attendre l'exécution de plusieurs fonctions simultanément (opération OR ou AND).
  • ✔Elles s'exécutent au niveau de privilège choisi à la création du gestionnaire.

Néanmoins, un gestionnaire ne peut pas référencer plus de 30 fonctions de rappel et chaque manager possède un nombre de messages limité.

4. Utilisation

Avant de pouvoir utiliser des fonctions de rappel, il est nécessaire de créer les deux managers en exécutant la fonction mk_callback_createManagers.

Cette fonction peut par exemple être exécutée dans le programme principal avant le démarrage du noyau : 


void mk_main ( void )
{
   /* Déclaration de la variable de retour */
   T_mkCode l_result = K_MK_OK;

   /* Initialisation du noyau */
   l_result = mk_init ( K_MK_MODE_FLOATING, g_mkProcessStack,
      K_MK_PROCESS_STACK_SIZE );

   /* Initialisation des managers de rappel en mode flottant */
   l_result |= mk_callback_createManagers ( K_MK_TYPE_FLOATING );

   /* Initialisation de la tâche de repos */
   l_result |= mk_createIdle ( g_mkIdleStack, K_MK_TASK_IDLE_STACK_SIZE,
      mk_task_idle, ( T_mkAddr ) "I" );

   /* Lancement du noyau avec un tick de 1 ms */
   l_result |= mk_start ( 27000 );

   /* ... */
   for ( ;; ) ;
}

La création des gestionnaires et des fonctions de rappel s'effectue avec les fonctions mk_callback_createHandler et mk_callback_create.


Une fonction de rappel peut recevoir jusqu'à six paramètres. Chacun d'eux occupe un mot 32 bits. La fonction peut ne déclarer que ceux dont elle a besoin et leur donner le type de son choix (code retour, entier, pointeur).


L'exemple ci-dessous montre la création d'un gestionnaire de rappel protégé et de deux fonctions de rappel : 


/* Pointeurs du gestionnaire et des fonctions de rappel */
K_MK_PRIVILEGED_BSS_MEMORY T_mkCallbackHandler* g_handler;
K_MK_PRIVILEGED_BSS_MEMORY T_mkCallback* g_callbackAcquire;
K_MK_PRIVILEGED_BSS_MEMORY T_mkCallback* g_callbackSend;

/* Mesure transmise à la fonction de rappel */
K_MK_PRIVILEGED_BSS_MEMORY uint32_t g_value;

/* Fonction de rappel de fin d'acquisition */
/* Le premier paramètre contient le code retour de l'acquisition, */
/* et le second l'adresse de la mesure. */
/* Les quatre autres paramètres ne sont pas utilisés. */
void app_onAcquire ( T_mkCode p_err, uint32_t* p_value )
{
   if ( p_err == K_MK_OK ) {
      /* Traitement de la mesure ... */
   }
   else {
      /* Gestion de l'erreur ... */
   }
}

/* Fonction de rappel de fin d'envoi */
/* Seul le code retour est utilisé. */
void app_onSend ( T_mkCode p_err )
{
   /* ... */
}

/* Une tâche privilégiée */
void mk_task_privileged ( T_mkAddr p_param )
{
   /* Déclaration de la variable de retour */
   T_mkCode l_result;

   /* Création d'un gestionnaire protégé */
   /* Il est rattaché au manager privilégié et ne peut être manipulé */
   /* que par des tâches privilégiées */
   l_result = mk_callback_createHandler ( &g_handler, K_MK_AREA_PROTECTED );

   /* Si le gestionnaire a été créé */
   if ( l_result == K_MK_OK )
   {
      /* Création des deux fonctions de rappel */
      /* L'adresse de la fonction doit être convertie en T_mkAddr */
      l_result = mk_callback_create ( g_handler, K_MK_AREA_PROTECTED,
         &g_callbackAcquire, ( T_mkAddr ) app_onAcquire );

      l_result |= mk_callback_create ( g_handler, K_MK_AREA_PROTECTED,
         &g_callbackSend, ( T_mkAddr ) app_onSend );
   }

   /* ... */
   for ( ;; ) ;
}

L'exécution d'une fonction de rappel est déclenchée avec la fonction mk_callback_trig. L'application place d'abord les six paramètres de la fonction dans une structure de type T_mkCallbackParam qui sera copiée dans la boîte de messages du manager. La fonction de rappel sera ensuite exécutée de manière différée.

L'exemple ci-dessous déclenche la fonction app_onAcquire à la fin d'une acquisition : 


/* Une tâche privilégiée qui réalise des acquisitions */
void app_task_acquisition ( T_mkAddr p_param )
{
   /* Déclaration des variables de travail */
   T_mkCode l_result;
   T_mkCode l_status;

   /* Déclaration de la structure contenant les paramètres de la fonction */
   /* de rappel. Elle est copiée avant le retour de mk_callback_trig,  */
   /* une variable locale peut donc être utilisée */
   T_mkCallbackParam l_param;

   while ( 1 )
   {
      /* Acquisition d'une mesure dans g_value ... */
      l_status = K_MK_OK;

      /* Écriture des paramètres de la fonction app_onAcquire */
      l_param.param1 = ( T_mkAddr ) l_status;  /* Statut de l'acquisition */
      l_param.param2 = ( T_mkAddr ) &g_value;  /* Adresse de la mesure */
      l_param.param3 = K_MK_NULL;
      l_param.param4 = K_MK_NULL;
      l_param.param5 = K_MK_NULL;
      l_param.param6 = K_MK_NULL;

      /* Déclenchement de la fonction de rappel */
      /* Celle-ci sera exécutée de manière différée. La tâche peut donc */
      /* réaliser d'autres opérations en attendant sa complétude */
      l_result = mk_callback_trig ( g_callbackAcquire, &l_param );

      if ( l_result == K_MK_OK ) {
         /* La fonction de rappel a été postée dans la boîte du manager */
      }
      else {
         /* Gestion des erreurs ...  */
         /* K_MK_ERROR_PARAM, K_MK_ERROR_ISR, K_MK_ERROR_RIGHT */
      }
   }
}

💬

Lorsque la boîte de messages du manager est pleine, la fonction mk_callback_trig bloque la tâche jusqu'à ce qu'un emplacement se libère. Le nombre de fonctions pouvant être en attente est défini par la constante K_MK_CALLBACK_MESSAGES_NUMBER.


⚠️

Le noyau copie la valeur des paramètres mais il ne copie pas les données qu'ils référencent. Dans l'exemple ci-dessus, la variable g_value doit rester valide et ne pas être modifiée tant que la fonction app_onAcquire n'a pas été exécutée. La fonction mk_callback_wait permet de s'en assurer.


Une tâche attend ensuite l'exécution d'une ou plusieurs fonctions de rappel avec la fonction mk_callback_wait. Le paramètre p_mkIdentifiers regroupe les identifiants attendus et les options de contrôle propres aux champs d'événements. Le paramètre p_mkTimeout définit la durée maximale de blocage.


L'exemple ci-dessous complète la tâche précédente. Celle-ci a terminé son travail et attend maintenant la fin de l'exécution de la fonction app_onAcquire pour recommencer un nouveau cycle d'acquisition : 


/* Suite de la tâche app_task_acquisition */
uint32_t l_flag;

/* Attente de l'exécution de la fonction app_onAcquire */
/* L'identifiant attendu est remis à zéro au réveil de la tâche */
l_result = mk_callback_wait ( g_handler,
   g_callbackAcquire->identifier | K_MK_EVENT_OR | K_MK_EVENT_CLEAR,
   &l_flag, 100 );

if ( l_result == K_MK_OK ) {
   /* La fonction app_onAcquire a été exécutée */
   /* La variable g_value peut être réutilisée */
}
else if ( l_result == K_MK_ERROR_TIMEOUT ) {
   /* La fonction n'a pas été exécutée pendant 100 ticks */
   /* La variable g_value ne doit pas être modifiée */
}
else {
   /* Gestion des erreurs ...  */
   /* K_MK_ERROR_PARAM, K_MK_ERROR_ISR, K_MK_ERROR_RIGHT */
   /* K_MK_ERROR_UNEXPECTED */
}

💬

Si le paramètre p_mkTimeout est nul et si aucune des fonctions attendues n'a été exécutée alors la fonction mk_callback_wait retourne immédiatement l'erreur K_MK_ERROR_TIMEOUT.


💬

Un timeout n'annule pas l'exécution de la fonction de rappel. Celle-ci reste en attente d'exécution dans la boîte de messages de son manager.


L'option K_MK_EVENT_OR réveille la tâche dès qu'une des fonctions référencées a été exécutée et le paramètre p_mkOutIdentifiers permet de déterminer lesquelles. L'option K_MK_EVENT_AND permet d'attendre que toutes les fonctions de rappel référencées aient été exécutées.

L'exemple ci-dessous bloque la tâche jusqu'à l'exécution des fonctions de fin d'acquisition et de fin d'envoi :


/* Attente de l'exécution des deux fonctions de rappel (AND) */
/* La tâche est bloquée indéfiniment tant que les deux fonctions */
/* n'ont pas été exécutées */
l_result = mk_callback_wait ( g_handler,
   g_callbackAcquire->identifier | g_callbackSend->identifier |
   K_MK_EVENT_AND | K_MK_EVENT_CLEAR, &l_flag, K_MK_TASK_WAIT_FOREVER );

Un gestionnaire dispose d'un champ d'événements de type MULTI. Plusieurs tâches peuvent donc attendre simultanément l'exécution de ses fonctions de rappel. Les règles de réveil sont celles décrites dans l'article Synchroniser les tâches avec les champs d'événements. Pour réveiller plusieurs tâches avec la même fonction de rappel, celles-ci doivent utiliser l'option K_MK_EVENT_NO_CLEAR.


Les dernières fonctions de l'API sont les fonctions mk_callback_delete et mk_callback_deleteHandler. Elles détruisent respectivement une fonction et un gestionnaire de rappel en demandant au noyau de les désallouer. Les fonctions de rappel doivent obligatoirement être supprimées avant leur gestionnaire :


/* Suppression des fonctions de rappel */
l_result  = mk_callback_delete ( g_callbackAcquire );
l_result |= mk_callback_delete ( g_callbackSend );

/* Suppression du gestionnaire */
/* Il ne doit plus référencer aucune fonction de rappel */
l_result |= mk_callback_deleteHandler ( g_handler );

/* Si une erreur s'est produite */
if ( l_result != K_MK_OK )
{
   /* Gestion des erreurs ...  */
   /* K_MK_ERROR_PARAM, K_MK_ERROR_ISR, K_MK_ERROR_RIGHT */
}

⚠️

La suppression d'un gestionnaire échoue avec l'erreur K_MK_ERROR_PARAM tant qu'il référence au moins une fonction de rappel.


⚠️

La suppression d'un gestionnaire détruit son champ d'événements. Les tâches bloquées par la fonction mk_callback_wait sont alors réveillées et retournent l'erreur K_MK_ERROR_UNEXPECTED.


⚠️

Le noyau ne vérifie pas si une fonction de rappel est en attente d'exécution dans la boîte de messages d'un manager avant de la supprimer. Il faut donc s'assurer qu'elle a bien été exécutée avant de la supprimer (fonction mk_callback_wait).


En effet, si une fonction de rappel est supprimée puis recréée alors que son ancien message est toujours en attente, le manager ne peut pas distinguer les deux instances (le même emplacement mémoire peut être réutilisé). Il exécute alors la nouvelle fonction avec les paramètres de l'ancien message et positionne l'identifiant de la nouvelle fonction comme si celle-ci avait été déclenchée.

5. Fonction synchrone ou asynchrone

Les fonctions de rappel peuvent rendre non bloquantes les fonctions d'une API logicielle. Pour ce faire, un modèle producteur/consommateur basé sur des requêtes et une tâche de traitement doit être mis en œuvre. Un paramètre contenant un pointeur de type T_mkCallback* doit alors être ajouté à chaque fonction :

  • ✔Lorsque ce paramètre est nul, la fonction sera bloquante ou synchrone. La tâche sera suspendue tant que la requête n'aura pas été exécutée par la tâche de traitement.
  • ✔Lorsque ce paramètre référence une fonction de rappel, la fonction sera non bloquante ou asynchrone. Elle retournera immédiatement et le résultat de celle-ci ne sera pas disponible.

L'exemple ci-dessous reprend ce principe de manière simplifiée. La fonction app_send transmet d'abord une requête à la tâche de traitement par l'intermédiaire d'une boîte de messages : 


/* Boîte de messages des requêtes d'envoi */
K_MK_UNPRIVILEGED_BSS_MEMORY T_mkMail* g_sendMail;

/* Structure d'une requête d'envoi */
typedef struct T_appMessage T_appMessage;
struct T_appMessage
{
   uint32_t* data;           /* Adresse des données à envoyer */
   uint32_t size;            /* Nombre de mots à envoyer */
   T_mkCode* result;         /* Adresse du code retour (requête bloquante) */
   T_mkCallback* callback;   /* Fonction de rappel (requête non bloquante) */
};

/* Fonction d'envoi bloquante ou non bloquante selon p_callback */
T_mkCode app_send ( uint32_t* p_data, uint32_t p_size, 
   T_mkCallback* p_callback )
{
   /* Déclaration des variables de travail */
   T_mkCode l_result;
   T_mkCode l_requestResult = K_MK_ERROR_UNEXPECTED;

   /* La tâche est suspendue par défaut */
   uint32_t l_state = K_MK_STATE_SUSPENDED;

   /* Déclaration de la requête */
   T_appMessage l_message = { p_data, p_size, &l_requestResult, p_callback };

   /* Si une fonction de rappel a été référencée, la tâche ne doit pas */
   /* être suspendue */
   if ( p_callback != K_MK_NULL )
   {
      l_state = K_MK_STATE_READY;
   }

   /* Transmission de la requête à la tâche de service */
   /* En mode bloquant, la tâche est suspendue jusqu'à la fin de */
   /* la requête */
   l_result = mk_mail_post ( g_sendMail, ( T_mkAddr ) &l_message, 
      l_state, K_MK_TASK_WAIT_FOREVER );

   /* Si la requête s'est exécutée de manière synchrone, le résultat est */
   /* écrit dans la variable de retour */
   if ( ( l_result == K_MK_OK ) && ( p_callback == K_MK_NULL ) )
   {
      l_result = l_requestResult;
   }

   return ( l_result );
}

La tâche de traitement reçoit alors le message et exécute la requête. Si une fonction de rappel a été référencée, elle déclenche son exécution. Dans le cas contraire, elle écrit le résultat de la requête dans le pointeur de la tâche appelante et la réactive avec la fonction mk_task_resume : 


/* Tâche de traitement (privilégiée) */
void app_task_handle ( T_mkAddr p_param )
{
   /* Déclaration des variables de travail */
   T_mkCode l_result;
   T_mkTask* l_task = K_MK_NULL;
   T_appMessage l_message;
   T_mkCallbackParam l_param;

   while ( 1 )
   {
      /* Attente d'une requête */
      l_result = mk_mail_pend ( &l_task, 
         g_sendMail, ( T_mkAddr ) &l_message, K_MK_TASK_WAIT_FOREVER );

      /* Si une requête a été reçue */
      if ( ( l_result == K_MK_OK ) && ( l_task != K_MK_NULL ) )
      {
         /* Exécution de la requête */
         /* Écriture de l_message.size mots à l'adresse l_message.data ... */
         l_result = K_MK_OK;

         /* Si une fonction de rappel a été référencée (requête */
         /* non bloquante) */
         if ( l_message.callback != K_MK_NULL )
         {
            /* Configuration des arguments de la fonction de rappel */
            l_param.param1 = ( T_mkAddr ) l_result;
            l_param.param2 = ( T_mkAddr ) l_message.data;
            l_param.param3 = ( T_mkAddr ) l_message.size;
            l_param.param4 = K_MK_NULL;
            l_param.param5 = K_MK_NULL;
            l_param.param6 = K_MK_NULL;

            /* Déclenchement de la fonction de rappel */
            l_result = mk_callback_trig ( l_message.callback, &l_param );
         }

         /* Sinon (requête bloquante) */
         else
         {
            /* Écriture du résultat de la requête */
            *l_message.result = l_result;

            /* Réactivation de la tâche appelante */
            l_result = mk_task_resume ( l_task );
         }
      }
   }
}

Avec cette méthode, l'applicatif a la possibilité de choisir le comportement de la fonction app_send lors de chaque appel. En mode synchrone, la tâche est suspendue et réveillée quand le travail est terminé. En mode asynchrone, la tâche n'est pas suspendue, elle doit néanmoins attendre la fin de l'exécution de la fonction de rappel en utilisant mk_callback_wait :


/* Pointeurs du gestionnaire et des fonctions de rappel */
K_MK_PRIVILEGED_BSS_MEMORY T_mkCallbackHandler* g_handler;
K_MK_PRIVILEGED_BSS_MEMORY T_mkCallback* g_callbackTransfer;

/* Fonction de rappel (3 paramètres utilisés)*/
void app_onTransfer ( T_mkCode p_err, uint32_t* p_buf, uint32_t p_size )
{
   if ( p_err == K_MK_OK ) {
      /* Traitement ... */
   }
   else {
      /* Gestion de l'erreur ... */
   }
}

/* Une tâche privilégiée de l'application */
void mk_task_user ( T_mkAddr p_param )
{
   /* Déclaration des variables de travail */
   T_mkCode l_result;
   uint32_t l_flag;
   uint32_t l_data [ 4 ] = { 1, 2, 3, 4 };

   /* Création d'un gestionnaire protégé */
   l_result = mk_callback_createHandler ( &g_handler, K_MK_AREA_PROTECTED );

   /* Création d'une fonction de rappel protégée */
   l_result |= mk_callback_create ( g_handler, K_MK_AREA_PROTECTED,
      &g_callbackTransfer, ( T_mkAddr ) app_onTransfer );
   
   /* Envoi bloquant : la tâche est suspendue jusqu'à la fin de la requête */
   /* Le résultat est disponible dans la variable de retour */
   l_result |= app_send ( l_data, 4, K_MK_NULL );

   /* Envoi non bloquant : la fonction retourne dès que la requête */
   /* a été transmise. */
   l_result |= app_send ( l_data, 4, g_callbackTransfer );

   /* Si la requête a été transmise */
   if ( l_result == K_MK_OK )
   {
      /* La tâche peut réaliser un autre traitement ... */

      /* Attente de la fin de la requête */
      /* Le tableau l_data doit rester valide jusqu'à l'exécution de */
      /* app_onTransfer */
      l_result = mk_callback_wait ( g_handler,
         g_callbackTransfer->identifier | K_MK_EVENT_OR | K_MK_EVENT_CLEAR,
         &l_flag, K_MK_TASK_WAIT_FOREVER );
   }
}

💬

En mode non bloquant, la valeur de retour de la fonction app_send indique uniquement si la requête a été transmise ou non. Le résultat de la requête est transmis à l'applicatif par le biais de la fonction app_onTransfer et du paramètre p_err.


⚠️

En mode non bloquant, la requête est exécutée après le retour de la fonction app_send. Les données qu'elle référence ne sont pas copiées et doivent donc rester valides jusqu'à l'exécution de la fonction de rappel.


6. Protéger ses callbacks

Les gestionnaires et les fonctions de rappel peuvent être créés avec les attributs K_MK_AREA_PROTECTED ou K_MK_AREA_UNPROTECTED.


Lorsque l'attribut K_MK_AREA_PROTECTED est utilisé pour un gestionnaire, le champ d'événements et la boîte de messages du manager associés sont eux aussi protégés. Il est alors impossible pour une tâche non privilégiée de créer le gestionnaire, de le supprimer, de référencer, d'attendre ou de déclencher une fonction de rappel.


Le tableau ci-dessous résume les règles applicables à la création d'un gestionnaire :

Créateur Gestionnaire Manager associé Résultat
Tâche privilégiée Protégé Privilégié Manipulable par les tâches privilégiées uniquement
Tâche privilégiée Non protégé Non privilégié Manipulable par toutes les tâches
Tâche non privilégiée Non protégé Non privilégié Manipulable par toutes les tâches
Tâche non privilégiée Protégé - Erreur K_MK_ERROR_RIGHT

Une tâche non privilégiée ne peut donc créer que des gestionnaires ou des fonctions de rappel non protégés. Dans cette configuration, les fonctions de rappel s'exécutent en mode non privilégié et un accès à une zone privilégiée déclenche une erreur de la MPU.


Les gestionnaires et les fonctions de rappel étant alloués par le noyau dans l'espace privilégié, aucune règle de placement ne s'applique. Seules les variables stockant leurs adresses doivent être accessibles aux tâches qui les utilisent. Les règles de placement de ces variables sont détaillées dans l'article Protéger son programme avec Mk.

7. API

7.1. La fonction mk_callback_createManagers()

Cette fonction initialise les deux managers de rappel privilégié et non privilégié du noyau. Chaque manager est constitué d'une tâche, de sa pile et d'une boîte de messages.


Prototype :


T_mkCode mk_callback_createManagers ( uint32_t p_mkStackType );

Paramètres :

  • p_mkStackType [in]

    Type des tâches des deux managers. Les valeurs possibles sont les suivantes :

    • K_MK_TYPE_FLOATING : les tâches sont de type flottant. Les fonctions de rappel peuvent utiliser la FPU.
    • K_MK_TYPE_DEFAULT : les tâches des managers sont de type non flottant.

Retour :

  • K_MK_OK : les deux managers de rappel ont été créés.
  • K_MK_ERROR_PARAM : les managers n'ont pas été créés car au moins un paramètre est invalide.
  • K_MK_ERROR_MALLOC : les managers n'ont pas été créés car le nombre maximal de tâches, de boîtes de messages ou de messages pouvant être alloués a été atteint.
  • K_MK_ERROR_RIGHT : les managers n'ont pas été créés car une tâche non privilégiée ne peut pas créer une tâche privilégiée.
  • K_MK_ERROR_INIT : les managers n'ont pas été créés car le noyau n'est pas initialisé.
  • K_MK_ERROR_ISR : les managers n'ont pas été créés car cette fonction a été exécutée dans un vecteur d'interruption.

Note :

  • Cette fonction ne peut pas être exécutée dans un vecteur d'interruption.
  • Cette fonction doit être exécutée après l'initialisation du noyau et avant l'utilisation de toute autre fonction du module. Elle peut être appelée avant le démarrage du noyau.
  • Cette fonction consomme deux tâches, deux boîtes de messages et deux fois K_MK_CALLBACK_MESSAGES_NUMBER messages.
  • La taille de la pile et la priorité des tâches des managers sont définies à la compilation (voir les définitions).
7.2. La fonction mk_callback_createHandler()

Cette fonction crée un gestionnaire de rappel.


Prototype :


T_mkCode mk_callback_createHandler ( T_mkCallbackHandler** p_mkHandler, 
   uint32_t p_mkAreaType );

Paramètres :

  • p_mkHandler [out]

    Adresse d'un pointeur de type T_mkCallbackHandler*.


  • p_mkAreaType [in]

    Type de protection du gestionnaire. Les valeurs possibles sont les suivantes :

    • K_MK_AREA_PROTECTED : le gestionnaire est protégé, il ne peut pas être manipulé par des tâches non privilégiées. S'il est créé par une tâche privilégiée, ses fonctions de rappel sont exécutées par le manager privilégié.
    • K_MK_AREA_UNPROTECTED : le gestionnaire n'est pas protégé, il peut être manipulé par des tâches privilégiées ou non privilégiées. Ses fonctions de rappel sont exécutées par le manager non privilégié.

Retour :

  • K_MK_OK : le gestionnaire de rappel a été créé.
  • K_MK_ERROR_PARAM : le gestionnaire de rappel n'a pas été créé car au moins un paramètre est invalide.
  • K_MK_ERROR_MALLOC : le gestionnaire de rappel n'a pas été créé car le nombre maximal de gestionnaires ou de champs d'événements pouvant être alloués a été atteint.
  • K_MK_ERROR_ISR : le gestionnaire de rappel n'a pas été créé car cette fonction a été exécutée dans un vecteur d'interruption.
  • K_MK_ERROR_RIGHT : le gestionnaire de rappel n'a pas été créé car une tâche non privilégiée ne peut pas créer un gestionnaire protégé.

Note :

  • Cette fonction ne peut pas être exécutée dans un vecteur d'interruption.
  • Chaque gestionnaire consomme un champ d'événements. Les constantes K_MK_SCHEDULER_MAX_NUMBER_OF_CALLBACK_HANDLERS et K_MK_SCHEDULER_MAX_NUMBER_OF_EVENTS définissent donc le nombre maximal de gestionnaires pouvant être créés.
7.3. La fonction mk_callback_create()

Cette fonction crée une fonction de rappel et la référence dans un gestionnaire.


Prototype :


T_mkCode mk_callback_create ( T_mkCallbackHandler* p_mkHandler, 
   uint32_t p_mkAreaType, T_mkCallback** p_mkCallback, 
   T_mkAddr p_mkFunction );

Paramètres :

  • p_mkHandler [in]

    Adresse d'un gestionnaire de type T_mkCallbackHandler.


  • p_mkAreaType [in]

    Type de protection de la fonction de rappel. Les valeurs possibles sont les suivantes :

    • K_MK_AREA_PROTECTED : la fonction de rappel est protégée, elle ne peut pas être manipulée par des tâches non privilégiées.
    • K_MK_AREA_UNPROTECTED : la fonction de rappel n'est pas protégée, elle peut être manipulée par des tâches privilégiées ou non privilégiées.
  • p_mkCallback [out]

    Adresse d'un pointeur de type T_mkCallback*.


  • p_mkFunction [in]

    Adresse de la fonction à exécuter. Cette fonction peut déclarer jusqu'à six paramètres 32 bits (T_mkCallbackFunction).

Retour :

  • K_MK_OK : la fonction de rappel a été créée.
  • K_MK_ERROR_PARAM : la fonction de rappel n'a pas été créée car au moins un paramètre est invalide ou car le gestionnaire a été détruit.
  • K_MK_ERROR_MALLOC : la fonction de rappel n'a pas été créée car le nombre maximal de fonctions de rappel du gestionnaire (30) ou le nombre maximal de fonctions pouvant être allouées a été atteint.
  • K_MK_ERROR_ISR : la fonction de rappel n'a pas été créée car cette fonction a été exécutée dans un vecteur d'interruption.
  • K_MK_ERROR_RIGHT : la fonction de rappel n'a pas été créée car une tâche non privilégiée ne peut pas créer une fonction protégée ou référencer une fonction dans un gestionnaire protégé.

Note :

  • Cette fonction ne peut pas être exécutée dans un vecteur d'interruption.
  • Un gestionnaire peut référencer 30 fonctions de rappel au maximum. La constante K_MK_SCHEDULER_MAX_NUMBER_OF_CALLBACK_FUNCTIONS définit le nombre maximal de fonctions de rappel pouvant être créées, tous gestionnaires confondus.
  • Le niveau d'exécution de la fonction (privilégié ou non) est celui du manager associé au gestionnaire.
7.4. La fonction mk_callback_trig()

Cette fonction transmet un message au manager d'une fonction de rappel pour déclencher son exécution.


Prototype :


T_mkCode mk_callback_trig ( T_mkCallback* p_mkCallback, 
   T_mkCallbackParam* p_mkCallbackParam );

Paramètres :

  • p_mkCallback [in]

    Adresse de la fonction de rappel de type T_mkCallback à exécuter.


  • p_mkCallbackParam [in]

    Adresse d'une structure de type T_mkCallbackParam contenant la valeur des six paramètres de la fonction. Les paramètres inutilisés par la fonction de rappel peuvent prendre la valeur K_MK_NULL.

Retour :

  • K_MK_OK : la demande d'exécution de la fonction de rappel a été envoyée à son manager.
  • K_MK_ERROR_PARAM : la demande d'exécution n'a pas été envoyée car la fonction de rappel est invalide.
  • K_MK_ERROR_ISR : la demande d'exécution n'a pas été envoyée car la fonction a été exécutée dans un vecteur d'interruption.
  • K_MK_ERROR_RIGHT : la demande d'exécution n'a pas été envoyée car une tâche non privilégiée ne peut pas manipuler un gestionnaire ou une fonction protégée.

Note :

  • Cette fonction ne peut pas être exécutée dans un vecteur d'interruption.
  • Le contenu de la structure T_mkCallbackParam est copié dans la boîte de messages avant le retour de la fonction. Elle peut donc être stockée dans une variable locale.
  • Lorsque la boîte de messages du manager est pleine, la tâche est bloquée jusqu'à ce qu'un emplacement se libère. Le nombre total de messages est défini par la constante K_MK_CALLBACK_MESSAGES_NUMBER.
  • Les fonctions de rappel d'un même manager sont exécutées dans leur ordre d'arrivée.

Attention :

⚠️

  • Seules les valeurs des paramètres sont copiées. Les données qu'ils référencent doivent rester valides jusqu'à l'exécution de la fonction de rappel.
7.5. La fonction mk_callback_wait()

Cette fonction attend l'exécution d'une ou plusieurs fonctions de rappel d'un gestionnaire. Si la condition n'est pas satisfaite, la tâche peut être bloquée en attendant que les fonctions soient exécutées.


Prototype :


T_mkCode mk_callback_wait ( T_mkCallbackHandler* p_mkHandler, 
   uint32_t p_mkIdentifiers, uint32_t* p_mkOutIdentifiers, 
   uint32_t p_mkTimeout );

Paramètres :

  • p_mkHandler [in]

    Adresse d'un gestionnaire de type T_mkCallbackHandler.


  • p_mkIdentifiers [in]

    Identifiants des fonctions de rappel attendues combinés avec les options de contrôle. Les constantes suivantes peuvent être utilisées :

    • K_MK_EVENT_OR : la condition est satisfaite lorsqu'au moins une fonction attendue a été exécutée.
    • K_MK_EVENT_AND : la condition est satisfaite lorsque toutes les fonctions attendues ont été exécutées.
    • K_MK_EVENT_CLEAR : les identifiants attendus sont remis à zéro lorsque la condition est satisfaite.
    • K_MK_EVENT_NO_CLEAR : les identifiants attendus ne sont pas remis à zéro lorsque la condition est satisfaite.
  • p_mkOutIdentifiers [out]

    Adresse d'une variable stockant les identifiants des fonctions de rappel exécutées.


  • p_mkTimeout [in]

    Durée maximale de blocage de la tâche. Les valeurs possibles sont les suivantes :

    • 0x0 : la fonction retourne immédiatement si la condition n'est pas satisfaite.
    • 0x1 à 0xFFFFFFFE : la tâche est bloquée pendant la durée spécifiée (en multiple de tick) tant que la condition n'est pas satisfaite.
    • 0xFFFFFFFF (K_MK_TASK_WAIT_FOREVER) : la tâche est bloquée tant que la condition n'est pas satisfaite.

Retour :

  • K_MK_OK : la ou les fonctions de rappel ont été exécutées.
  • K_MK_ERROR_PARAM : l'exécution des fonctions de rappel n'a pas été vérifiée car au moins un paramètre est invalide.
  • K_MK_ERROR_TIMEOUT : une ou plusieurs fonctions de rappel n'ont pas été exécutées dans le délai imparti.
  • K_MK_ERROR_ISR : l'exécution des fonctions de rappel n'a pas été vérifiée car la fonction a été exécutée dans un vecteur d'interruption.
  • K_MK_ERROR_RIGHT : l'exécution des fonctions de rappel n'a pas été vérifiée car une tâche non privilégiée ne peut pas manipuler un gestionnaire protégé.
  • K_MK_ERROR_UNEXPECTED : l'exécution des fonctions de rappel n'a pas été vérifiée car le gestionnaire a été détruit pendant que la tâche était bloquée.

Note :

  • Cette fonction ne peut pas être exécutée dans un vecteur d'interruption.
  • Le champ d'événements d'un gestionnaire étant de type MULTI, plusieurs tâches peuvent être en attente de l'exécution des fonctions de rappel. Dans cette situation, elles sont examinées par ordre de priorité décroissante.
  • Un timeout n'annule pas l'exécution des fonctions de rappel.
7.6. La fonction mk_callback_delete()

Cette fonction détruit une fonction de rappel et la retire de son gestionnaire. Son identifiant peut alors être réattribué.


Prototype :


T_mkCode mk_callback_delete ( T_mkCallback* p_mkCallback );

Paramètres :

  • p_mkCallback [in, out]

    Adresse d'une structure de type T_mkCallback.

Retour :

  • K_MK_OK : la fonction de rappel a été détruite.
  • K_MK_ERROR_PARAM : la fonction de rappel n'a pas été détruite car le paramètre est invalide.
  • K_MK_ERROR_ISR : la fonction de rappel n'a pas été détruite car la fonction a été exécutée dans un vecteur d'interruption.
  • K_MK_ERROR_RIGHT : la fonction de rappel n'a pas été détruite car une tâche non privilégiée ne peut pas manipuler une fonction de rappel protégée.

Note :

  • Cette fonction ne peut pas être exécutée dans un vecteur d'interruption.

Attention :

⚠️

  • Le noyau ne vérifie pas si la fonction de rappel est en attente d'exécution dans la boîte de messages d'un manager. Il est donc nécessaire de s'assurer qu'elle ait bien été exécutée avant de la détruire. En effet, une fonction de rappel supprimée puis recréée alors que son ancien message est toujours en attente peut être confondue avec la nouvelle.
  • Étant donné que le même emplacement mémoire peut être réutilisé, le manager ne pourra pas distinguer les deux instances. Il exécutera alors la nouvelle fonction avec les paramètres de l'ancien message et positionnera l'identifiant de la nouvelle fonction comme si celle-ci avait été déclenchée.
7.7. La fonction mk_callback_deleteHandler()

Cette fonction détruit un gestionnaire de rappel ainsi que son champ d'événements.


Prototype :


T_mkCode mk_callback_deleteHandler ( 
   T_mkCallbackHandler* p_mkCallbackHandler );

Paramètres :

  • p_mkCallbackHandler [in, out]

    Adresse d'une structure de type T_mkCallbackHandler.

Retour :

  • K_MK_OK : le gestionnaire de rappel a été détruit.
  • K_MK_ERROR_PARAM : le gestionnaire de rappel n'a pas été détruit car le paramètre est invalide ou car il référence au moins une fonction de rappel.
  • K_MK_ERROR_ISR : le gestionnaire de rappel n'a pas été détruit car la fonction a été exécutée dans un vecteur d'interruption.
  • K_MK_ERROR_RIGHT : le gestionnaire de rappel n'a pas été détruit car une tâche non privilégiée ne peut pas manipuler un gestionnaire protégé.

Note :

  • Cette fonction ne peut pas être exécutée dans un vecteur d'interruption.
  • Les fonctions de rappel du gestionnaire doivent être détruites avec la fonction mk_callback_delete avant la destruction du gestionnaire.

Attention :

⚠️

  • Lorsque le gestionnaire est détruit, les tâches bloquées par la fonction mk_callback_wait sont réveillées. Elles retournent alors l'erreur K_MK_ERROR_UNEXPECTED.
7.8. Les définitions

Le module callback peut être configuré à l'aide des définitions suivantes :

Définition Description Valeur
K_MK_SCHEDULER_MAX_NUMBER_OF_CALLBACK_HANDLERS Cette constante définit le nombre de gestionnaires de rappel pouvant être créés. Elle ne peut pas être nulle. 32
K_MK_SCHEDULER_MAX_NUMBER_OF_CALLBACK_FUNCTIONS Cette constante définit le nombre de fonctions de rappel pouvant être créées, tous gestionnaires confondus. Elle ne peut pas être nulle. 32
K_MK_CALLBACK_STACK_SIZE Cette constante définit la taille de la pile de chaque manager de rappel (en multiple de mots 32 bits). 1024
K_MK_CALLBACK_PRIVILEGED_PRIORITY Cette constante définit la priorité du manager privilégié. 6
K_MK_CALLBACK_UNPRIVILEGED_PRIORITY Cette constante définit la priorité du manager non privilégié. 6
K_MK_CALLBACK_MESSAGES_NUMBER Cette constante définit le nombre de fonctions de rappel pouvant être en attente d'exécution dans la boîte de messages de chaque manager. Elle ne peut pas être nulle. 8
